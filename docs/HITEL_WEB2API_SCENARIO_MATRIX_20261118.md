# HITEL Web2API — 저장 계정 사용자 시나리오 검증서

- 시험 계정: 사용자가 직접 등록하고 GitHub Actions에 AES-GCM 암호화 저장한 **1번 계정**
- 서버: GitHub Actions 임시 Chrome + 고정된 `MartinezS8/chatgpt-web2api` 원본 + 최소 DOM 패치
- 운영 제약: **Railway 사용·재배포·재시작 없음**, GitHub Pages는 정적 페이지
- 개인정보: 실제 이메일·쿠키·토큰·대화 ID를 로그와 결과 파일에 기록하지 않음
- 데이터: 임의 생성한 텍스트·TXT·CSV만 사용하며, 기존 사용자 파일은 읽거나 삭제하지 않음
- 주의: 실제 질문 시험은 **테스트용 새 ChatGPT 대화를 생성**합니다. 해당 대화는 ChatGPT 기록에 남을 수 있습니다.

| ID | 사용자 행동 시나리오 | 검증 방법 | 합격 기준 |
| --- | --- | --- | --- |

| S03 | 새 대화로 한국어 질문 | 한국어 요청으로 독립 대화 시작 | HTTP 200과 정확한 한국어 시험 표식 포함 |
| S04 | 같은 대화에서 연속 2회 질문 | 첫 발화에만 임의 코드 입력, 둘째 발화에서 해당 코드 요청 | 동일한 대화 ID와 이전 코드 회신 |
| S05 | 새 대화 생성 및 분리 | S02와 S03의 응답 대화 ID 비교 | 서로 다른 대화 ID |
| S06 | 실시간 스트리밍 질문 | `stream=true` SSE 전송 | 표식 수신과 정상 종료 표시 |
| S07 | Web2API로 파일 첨부 | 고정 원본 REST API의 파일 전송 인터페이스 검사 | 미구현 시 `UNSUPPORTED`를 정직하게 보고 |
| S08 | ChatGPT Chrome에서 TXT 파일 첨부 | 새 테스트 대화에 합성 TXT 파일 선택 | 첨부 파일 표시 확인 |
| S09 | 전송 전 첨부 파일 제거 | 첨부 상태에서 제거 버튼 사용 | 파일이 메시지에서 사라짐 |
| S10 | 업로드한 TXT 내용 질문 | 테스트 파일 안의 임의 값을 질문에 노출하지 않은 채 요청 | 실제 파일 값이 답변에 포함 |
| S11 | ChatGPT가 생성한 파일 내려받기 | 다운로드 가능한 파일 링크와 실제 저장 여부 검사 | 파일 저장 및 0바이트 초과 |
| S12 | 등록하지 않은 다른 계정 사용 방지 | 저장 계정 목록과 프로필 개수 확인 | 미등록 2번 프로필을 1번 계정으로 대체하지 않음 |
| S13 | 파일 첨부 정보를 위조해 작업 요청 | 릴레이의 바이너리 거부 회귀시험 | 실제 메시지 전송 전에 거부 |
| S14 | 다른 대화의 ID로 답변 끼워넣기 | 잘못된 대화 ID의 응답 수용 여부 시험 | 요청 대화 ID가 다르면 결과 거부 |

## 결과 해석 원칙

- **PASS:** 해당 검증 절차를 실제 실행하고 합격 조건 확인
- **FAIL:** 실제 실행했으나 합격 조건 미충족
- **UNSUPPORTED:** 기존 원본 Web2API의 기능 자체가 없음
- **BLOCKED:** 다른 선행 조건이나 현재 ChatGPT 화면에 의해 시험 자체가 성립하지 않음

이 시나리오는 ChatGPT **웹 UI 직접 조작**과 **기존 Web2API REST 호출**을 구분합니다. 웹 UI에서 TXT 첨부가 성공하더라도 그것이 곧 Web2API 파일 전송 기능의 성공은 아닙니다.

## 추가 개선 범위

Web2API를 통해 PDF·TXT·이미지 등 바이너리를 직접 첨부하려면, 원본의 CDP 파일 업로드와 실제 파일 처리 결과 검증, 첨부 제거, 콘텐츠 ID 매핑이 별도 구현되어야 합니다. 구현되지 않은 경로를 파일명만 문자로 전송하는 방식으로 대체하지 않습니다.

## 2차 실제 시험 — 새 대화·SSE 오류 수정

실행: https://github.com/lyonbegin/procureflow/actions/runs/44205338405

- **S05 PASS**: 새 `new_conversation=true` 선택 시 서로 다른 대화 ID 생성
- **S06 PASS**: SSE 표식, `finish_reason=stop`, `[DONE]` 모두 확인
- S01–S04, S12–S14: 재시험에서 모두 PASS
- **S08 FAIL**: 이 실행에서는 TXT 파일 첨부 후 UI 파일 카드 표시가 확인되지 않음. 1차의 S08 PASS와 결과가 달라 불안정
- S09–S11: S08이 확인되지 않아 BLOCKED
- S07: 원본 Web2API의 파일 업로드 API 미구현으로 UNSUPPORTED

**2차 합계:** PASS 9 / FAIL 1 / UNSUPPORTED 1 / BLOCKED 3.

S05의 원본 문제: 대화 ID가 없는 요청을 무조건 새 대화로 처리하지 않고 기본적으로 이전 대화에 이어 붙이므로, 고정 원본에 **선택적인 `new_conversation` 플래그만 추가**했습니다. 기존 생략 시 이어쓰기 동작은 그대로 유지합니다.

파일 항목은 별도의 **실제 Chrome 파일 전용 3차 시험**으로 분리했습니다. 파일 첨부 카드가 보이는지, 보내기 전 삭제가 되는지, TXT·CSV의 실제 내용 질문이 가능한지, 생성 파일을 내려받을 수 있는지를 검사합니다.

## 종합 결론 및 미완료 개발 작업

1. 저장 계정 1번 복원, 영어·한국어 질문, 대화 이어가기, **명시적 새 대화 생성**, SSE 스트리밍 응답은 실제 GitHub Chrome 통합시험에서 검증 완료.
2. 고정 원본 Web2API는 바이너리 파일 업로드·제거·다운로드용 엔드포인트가 **현재 없음**. ChatGPT 브라우저의 TXT 카드 표시만 PASS.
3. 파일 지원을 완성하려면 실제 업로드 완료 상태를 감지하여 메시지 전송을 허용하고, 첨부 삭제 컨트롤을 정확히 매핑하며, 첨부 파일의 내용 질의 응답을 검증하고, 생성 결과의 다운로드 이벤트와 파일 무결성을 확인해야 합니다.
4. 두 번째 실제 계정은 아직 등록되지 않아 계정 간 동시 사용·격리의 **실계정 통합시험은 불가능**. 현재 확인된 것은 미등록 계정의 사용 차단에 관한 단위·저장소 검사입니다.
5. 테스트가 생성한 임시 질문 대화는 사용자 ChatGPT 기록에 남을 수 있으며, 기존 사용자의 대화·파일을 자동 삭제하지 않았습니다.
6. Railway 배포·재시작 없음. GitHub Actions의 임시 실행기에서만 시험.
