2-1. 질문이 들어올 때 작업자 자동 기동

HITEL 텍스트 API는 검증된 Bearer 키로 질문을 제출했을 때 Chrome 작업자가 꺼져 있으면 GitHub Actions 실행을 자동 요청하도록 구현했습니다. 장애·연결 끊김을 감지하고 SQLite 잠금으로 중복 기동을 억제하며, GitHub App 인증이 실패한 경우 별도로 구성된 저장소 전용 Actions 토큰으로 재시도합니다. GitHub 작업자 자체도 종료 시 대기 작업이 남았다면 서명 검증을 거쳐 후속 작업자를 실행할 수 있습니다. 이미 보낸 것으로 의심되는 질문은 자동 재전송하지 않습니다.

현재 실제 가동 조건: Railway의 GitHub App 변수(HITEL_GITHUB_APP_ID, HITEL_GITHUB_APP_INSTALLATION_ID, HITEL_GITHUB_APP_PRIVATE_KEY) 또는 제한된 HITEL_GITHUB_ACTIONS_TOKEN 중 한 방식이 먼저 등록되어 있어야 합니다. 설정이 없다면 자동 기동을 성공했다고 표시하지 않으며 워커 미연결 시 HTTP 503을 유지합니다. GitHub 예약 실행은 추가하지 않았습니다.

2. 호출 구조

외부 프로그램 → HTTPS /integrations/v1/* → Bearer 키 및 계정·방 검증 → 대기열 접수(HTTP 202) → GitHub Chrome 작업자 → 사용자 ChatGPT 계정 → 작업 결과 API.

반드시 구분하십시오.

  1. HTTP 200/201: 조회/리소스 생성 성공을 뜻합니다.
  2. HTTP 202: 메시지가 대기열에 접수되었다는 뜻이며, ChatGPT 전송·답변이 완료된 것이 아닙니다. 응답의 sent_to_chatgpt=false가 정상 설계입니다.
  3. GET /integrations/v1/jobs/{job_id}에서 status=completed이고 result_text가 있어야 최종 답변으로 취급할 수 있습니다.
  4. status=failed이면 error를 읽으십시오. queued/running이면 동일 작업 ID로 재조회하며 메시지 재전송은 하지 마십시오.
  5. worker_connected=false일 때는 운영용 질문을 제출하지 말고 의존성 복구를 기다리거나 장애를 노출하십시오.

3. 계정 연결·API 키 발급·작업자 실행

외부 프로그램은 ChatGPT/Google 비밀번호·쿠키 대신 브라우저 소유자가 발급하는 htli_... 키와 이에 고정된 oai_... account_id를 사용합니다.

  1. 계정 연결 페이지에서 일회성 연결코드를 발급받습니다. 처음 한 번만 필요합니다.
  2. GitHub Actions 실행 화면에서 operation=verify_or_pair을 선택하고 pairing_code를 입력한 뒤 실행합니다. Actions가 암호화된 등록 정보와 실제 ChatGPT Chrome 로그인 상태를 검증합니다. 공식 OpenAI OIDC는 아닙니다.
  3. 연결 페이지에서 상태를 확인하고 htli_ 인증키를 발급받습니다. 키는 한 번만 표시됩니다.
  4. 다음 접속부터는 계정 재등록이 필요 없습니다. 작업자 켜기 페이지를 열어 operation=worker_only, run_minutes=240 기본값으로 GitHub Run workflow를 눌러 켭니다. pairing_code는 비워 둡니다.
  5. worker_connected=true가 확인되면 대화방 생성 → 질문 접수 → job 조회 순서로 호출합니다.

주의: 단순 링크 클릭만으로 GitHub Actions가 시작되는 것은 아닙니다. GitHub 계정의 실행 승인 클릭이 필요하며, 예약 작업은 추가하지 않았습니다.

메시지 요청 시 헤더는 Authorization: Bearer htli_...이고, 계정 식별자는 채팅 요청 JSON의 별도 account_id 필드에 넣습니다. 생성된 키는 GET /web/api/integrations/keys에서 메타데이터 조회, DELETE /web/api/integrations/keys/{key_id}에서 브라우저 CSRF 인증 후 폐기할 수 있습니다.

5. 외부 프로그램의 실제 호출 예시

아래 예시는 API 키와 실제 ChatGPT account_id가 이미 정상 발급되어 있고 worker_connected=true인 운영 환경을 전제로 합니다. 현재 서버에서는 준비가 끝나기 전까지 실행하지 마십시오.

A. 환경변수 및 사용 가능 여부

export BASE_URL="https://hitel-integration-api-production.up.railway.app"
export HITEL_API_KEY="htli_실제로_발급된_키"
export HITEL_ACCOUNT_ID="oai_실제로_발급된_계정_ID"

curl -sS "$BASE_URL/integrations/v1/capabilities"

worker_connected=false라도 GitHub 실행 인증이 설정된 경우 HTTP 202로 접수하고 작업자를 자동 기동합니다. 인증이 없는 경우 HTTP 503입니다. 실제 상태 확인

B. 대화방 생성

curl -sS -X POST "$BASE_URL/integrations/v1/rooms" \
  -H "Authorization: Bearer $HITEL_API_KEY" \
  -H "Content-Type: application/json" \
  --data '{"title":"외부 프로그램 새 대화방"}'

성공은 HTTP 201이며, 반환값 room_id와 account_id를 저장합니다. 방 제목은 1~160자입니다. 방은 해당 계정에 고정됩니다. 최대 방 수에는 서버의 웹 프로필별 한도가 적용됩니다.

C. 질문 접수

curl -i -X POST "$BASE_URL/integrations/v1/chat" \
  -H "Authorization: Bearer $HITEL_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: client-20261119-req-000001" \
  --data '{
    "room_id":"room_<실제 생성된 32자리 hex ID>",
    "account_id":"oai_<키와 같은 검증 계정 ID>",
    "text":"안녕하세요. 한 문장으로 답변해 주십시오.",
    "attachment_ids":[]
  }'

HTTP 202 응답 형식:

{
  "job_id":"job_<32자리 hex ID>",
  "status":"queued",
  "replayed":false,
  "accepted":true,
  "sent_to_chatgpt":false,
  "worker_connected":true,
  "poll":"/integrations/v1/jobs/job_<32자리 hex ID>"
}

이 예시의 worker_connected=true는 정상 연결되었을 때의 형식 예시이며 현시점 실서버 값은 false입니다.

  • text: 공백 제외 유효한 1~2,000자.
  • account_id: 키에 고정된 oai_ 식별자와 완전히 동일해야 합니다. 다르면 HTTP 409.
  • room_id: 발급된 room_ 뒤 32자리 소문자 hex.
  • Idempotency-Key: 16~128자의 영숫자, 밑줄, 점, 콜론 또는 하이픈. 같은 키·같은 요청을 다시 보내면 기존 job_id를 반환합니다. 같은 키로 다른 내용을 제출하면 HTTP 409입니다.
  • attachment_ids: 현재 반드시 빈 배열로 보내십시오. 파일 ID를 넣으면 HTTP 501입니다.

D. 질문 결과 조회

curl -sS "$BASE_URL/integrations/v1/jobs/job_<실제 받은 작업 ID>" \
  -H "Authorization: Bearer $HITEL_API_KEY"
{
  "job_id":"job_<작업 ID>",
  "room_id":"room_<대화방 ID>",
  "status":"completed",
  "stage":"<서버가 기록한 단계>",
  "result_text":"<실제 검증 후 얻은 답변>",
  "error":null,
  "created_at":0,
  "updated_at":0
}

위 JSON은 응답 스키마 예시이며 실제 사용자 답변 결과가 아닙니다. created_at/updated_at은 실제 응답에서 Unix 밀리초 단위로 들어옵니다. completed 이전에는 result_text가 null입니다. failed라면 error를 점검하십시오.

같은 방 후속 질문은 직전 job이 completed이고 기존 ChatGPT 대화방 연결이 검증된 경우에만 제출하십시오. 진행 중인 작업이 있으면 다른 키로 중복 질문을 생성하지 마십시오.

6. 오류 코드, 제한 및 재시도

HTTP의미프로그램의 동작
200조회 성공 또는 브라우저 키 발급해당 엔드포인트 반환값 확인
201새 대화방 생성room_id 저장
202작업 대기열 접수job_id 저장 후 GET으로 조회

401Authorization 없음Bearer 키 헤더 추가

404자신의 작업·키가 아니거나 존재하지 않음ID 및 소유권 검증
409계정 불일치, 이미 처리 중, 중복키 충돌, 계정 해제 등계정·방·작업 상태 확인 후 복구
422본문·ID 형식 검증 실패스키마에 맞게 수정
429과도한 호출 또는 키/방 한도전송 중지, 한도 확인

HITEL 자체의 시간당 5건 및 전체 하루 30건 채팅 제한은 제거했습니다. 방 단위 미완료 작업의 중복 방지와 Idempotency-Key 검사는 유지합니다. 활성 인증키 5개/프로필 한도는 채팅 횟수 제한과 무관합니다.

네트워크 타임아웃이 발생했을 때는 동일한 Idempotency-Key와 동일한 본문으로만 재확인하며, 성공적으로 접수된 작업은 GET jobs/{job_id}로 조회하십시오. HTTP 202를 실제 답변으로 보여주지 마십시오. 작업자가 끊긴 상태에서는 제출하지 않는 것을 원칙으로 합니다.

7. 파일 첨부 / 생성 파일 다운로드 — 정확한 현재 범위

일반 앱의 POST /integrations/v1/files는 HTTP 501입니다. 파일 첨부와 결과 파일 다운로드용 범용 API 계약이 만들어졌다고 보고하지 마십시오.

8. 실제 완료 항목과 별도 담당 개발자의 과제
